[導入・更新手順](../../README.md)

2026-10-08 には Excel の textconv 差分表示を Debian 13.6 のコンテナと Windows 11 の実機で、部分ステージを AlmaLinux 10.2 で確認しました。2026-10-09 には Windows 11 の実機で Excel の部分ステージを確認しました。2026-10-17 には Windows 11 の実機で、大きいブックの部分ステージを速くし、使うメモリを減らした版を確認しました。2026-10-18 には、2 つのブックの取り込み(`git excel-merge`)を Windows 11 と Raspberry Pi 5 の実機で確認しました。

## 2 つのブックの取り込み（2026-10-18）

`git excel-merge`（WinMerge と lazygit の専用画面）と、導入スクリプトの `alias.excel-merge`・`--uninstall` を、Windows 11 の実機と Raspberry Pi 5 の実機で確かめた。

- 環境（Windows）: Windows 11 Pro(ビルド 26300)、Git 2.55.0.windows.5、Python 3.14.8(scoop)、openpyxl 3.1.5、xlrd 2.0.2、lxml 6.1.3、WinMerge 2.16.58.2(winget の `WinMerge.WinMerge`、ユーザー単位)、lazygit 0.66.0・delta 0.20.1(scoop)、WezTerm 20260905-153129-092dcf70
- 環境（Linux）: Raspberry Pi 5 の AlmaLinux 10.2(aarch64。Python 3.14.8 と lazygit 0.66.0・delta 0.20.1 は Homebrew、Git 2.52.0、tmux next-3.4)。自動テストは同じ PC の WSL の AlmaLinux 10(Python 3.12.13、Git 2.52.0)でも走らせた
- 方法: `GIT_CONFIG_GLOBAL`・`XDG_CONFIG_HOME`(Linux は `XDG_DATA_HOME` も)を一時フォルダーに向け、`--install-dir` も一時フォルダーにして導入した。実際のグローバル Git 設定と導入先は変えていない
- 試験用のブック: openpyxl で作った `見積.xlsx`(取り込み先。シート `見積` と `備考`、見出しの行は太字と黄色の塗り)と `見積-更新.xlsx`(取り込み元。`見積` の B2・C3 の値、A4〜D4 を消して A5〜D5 を足し、D6 の数式を変えた。`備考` の B2 の値を変え、B3 をリッチテキストにした。見出しの塗りは青)

### 自動テストと導入

- `python -B -m unittest discover -s tests` は 159 件だった。Windows は 153 件が成功し、POSIX だけのテスト 6 件を飛ばした。WSL の AlmaLinux 10 と abiko-pi は 155 件が成功し、Windows だけのテスト 4 件を飛ばした
- 導入と `--check` は、どちらも「取り込み: git excel-merge」の行を出し、`alias.excel-merge` は `alias.excel-stage` と同じ build の `excel-stage.py` に `--merge` を付けた形だった(Windows と abiko-pi)
- Windows で `--uninstall` を 2 回走らせた。1 回目は 5 つの Git 設定・attributes の区画・導入先を消し、`core.attributesFile` は残った(attributes のファイルは区画だけを書いていたので 0 バイトになった)。2 回目は「消すものがありません」で終了コード 0 だった

### WinMerge

- Git のリポジトリの外のフォルダーで `git excel-merge -- 見積.xlsx 見積-更新.xlsx` を実行すると、端末に「書き換えるファイル」「取り込み元」の絶対パスと「取り込めない違い（1 セル）: 備考!B3（リッチテキスト）」が出て、WinMerge が別の窓で開いた。窓の題は「取り込み先（書き換える）: 見積.xlsx - 取り込み元: 見積-更新.xlsx」で、フォルダーのパスは出なかった。左右とも状態行は「UTF-8 BOM」「Unix」で、右は「RO」だった。差異は 5 件で、`備考` の B3 は左右とも取り込み先の行になっていた
- 保存せずに窓を閉じると、端末は窓を閉じるまで待ち、「取り込むセルが選ばれていません。取り込み先は変えていません。」で終了コード 0 だった
- 別の WinMerge(引数なし)を開いたままでも、取り込みの WinMerge は別のプロセスとして開き、その窓を閉じるまで待った(このときの WinMerge の設定は `SingleInstance` が 0)
- 取り込み先を別のプロセスが書き込みを拒む共有モード(`FileShare.Read`)で開いたままにすると、WinMerge を開く前に「取り込み先を Excel などで開いているなら閉じてからやり直してください」で止まり、終了コード 1 だった
- 50 万セルのブック(下の表)でも、WinMerge は約 1 秒で窓を開き、「10 件の差異が見つかりました」と出た

### lazygit の専用画面

- Windows の WezTerm(120 列×40 行)と abiko-pi の tmux(160 列×45 行)で、`git excel-merge --tool lazygit -- 見積.xlsx 見積-更新.xlsx` を開き、`002-備考.cells.txt` で `Enter` → `Space` → `X` を押した。どちらも「1 セルを取り込み先へ書き込みました。q で元の画面へ戻ってください。」が出て、`q` で閉じると「1 セルを取り込み先へ書き込みました: …」と終了コード 0 が出た
- 取り込み先は `備考` の B2 だけが「11 月 15 日」になり、`見積` の B2 は 10 のまま、見出しの A1 は太字と取り込み先の塗り(`FFF2CC`)のままだった。取り込み先のフォルダーに一時ファイルは残らず、一時フォルダー(`excel-merge-*`)も残らなかった

### 見つかった問題と対応

- WinMerge の終了コードを見て止める作りだったが、終了コードは取り込みの結果を表さないので見ないようにした。保存された左のテキストだけで判断する
- WinMerge を閉じた後に、照合と書き込みでブックを 2 回読んでいた。1 回だけ読むようにした
- `Zone.Identifier` を読めないファイルシステム(FAT やネットワークの共有など)で、書き込みが止まる作りだった。読めなければ引き継がずに書くようにした
- この確かめの作業環境は `NO_COLOR=1` を引き継いでいて、そのまま起動した lazygit と delta の画面に色が付かなかった。`NO_COLOR` を外して起動し直すと色が付いた(道具の不具合ではない)

## Windows 11 での大きいブックの部分ステージの高速化（2026-10-17）

大きいブックの読み取り・射影・選択の照合・再構成を速くし、使うメモリを減らした版を Windows 11 の実機で確かめた。専用画面を閉じた後の一時フォルダーの後片付けで見つかった問題にも対応した。

- 環境: Windows 11 Pro(ビルド 26300)、AMD Ryzen AI MAX+ 395(32 スレッド)、Git 2.55.0.windows.5、Python 3.14.8(scoop)、openpyxl 3.1.5、xlrd 2.0.2、lxml 6.1.3、lazygit 0.66.0・delta 0.20.1(scoop)、WezTerm 20260905-153129-092dcf70。Linux 側は同じ PC の WSL の AlmaLinux 10(Python 3.12.13、Git 2.52.0、openpyxl 3.1.5、lxml 6.1.3)を使った
- 計測用のブック: openpyxl で作った 10 列の表(数値と日本語の文字列)で、列 B の離れた 10 セルを変更した。10 万セルのもう 1 つは 1,000 セルを変更した
- 速さとメモリの計測: 計測用のスクリプトから `prepare_session`(`E` の処理)と `apply_session`(`X` の処理。全変更を選択)を直接呼んだ。修正前(`custom` の `3abbd33`)と修正後を交互に 3 回ずつ走らせ、中央値を使った。メモリはプロセスのピークのワーキングセットを測った。計測中は、ほかのセッションの処理(別のリポジトリの性能調査など)が同時に動いていて、CPU 使用率は計測の合間に 10〜57% だった。50 万セルの修正前の値は、同じ日に CPU 使用率 10% のときに同じスクリプトで測った値(`E` 19.69 秒・`X` 30.42 秒)より大きかった
- 実 TUI の方法: `GIT_CONFIG_GLOBAL`・`XDG_CONFIG_HOME`・`XDG_DATA_HOME` と `--install-dir` を一時フォルダーに向けて修正後の版を導入した。同梱 `config.yml` を `--use-config-file` で読む lazygit を、利用者の WezTerm 設定のまま 160 列×45 行の窓で起動した。キーは `wezterm cli send-text` で送り、画面は `wezterm cli get-text` で読み取った。実際のグローバル Git 設定と `%LOCALAPPDATA%` の導入先は変えていない

### 変更した処理

- ワークシートは行ごとに読み流し、lxml のツリーを持たないようにした。セル番地は 1 度だけ解析して数値の順序を持ち、射影の並べ替えと書き出しに使った
- 普通の数値と射影の行は速い経路で作った。`Decimal`・`json.dumps` と同じ結果になることをテストで確かめた
- 選択画面を作ったときの射影を一時セッションに残し、`X` では選択画面の行と比べて違う行だけを検査した。base・work のブックと射影はハッシュで確かめた
- 作り直すシートだけを元のバイト列から読み直し、書き出した結果は ZIP の全パーツのバイト列・構成・作り直したシートのセルで検証した

### 速さとメモリ

計測用のスクリプトから直接呼んだ各 3 回の中央値。時間は秒、メモリはプロセスのピークのワーキングセット。

| ブック | `E` 修正前 | `E` 修正後 | `X` 修正前 | `X` 修正後 | `E` のメモリ 修正前→後 | `X` のメモリ 修正前→後 |
| --- | ---: | ---: | ---: | ---: | --- | --- |
| `.xlsx` 100 セル | 1.51 | 1.47 | 0.46 | 0.39 | 27 MB → 27 MB | 28 MB → 28 MB |
| `.xlsx` 1 万セル | 1.85 | 1.59 | 1.09 | 0.74 | 58 MB → 36 MB | 79 MB → 45 MB |
| `.xlsx` 10 万セル(0.56 MB) | 5.91 | 2.99 | 8.31 | 2.79 | 325 MB → 113 MB | 521 MB → 200 MB |
| `.xlsx` 10 万セル、1,000 セル変更 | 5.48 | 2.81 | 7.32 | 2.75 | 325 MB → 113 MB | 537 MB → 200 MB |
| `.xlsx` 50 万セル(2.8 MB) | 25.50 | 9.91 | 37.97 | 17.28 | 1,476 MB → 453 MB | 2,476 MB → 878 MB |

- CPU 時間(プロセスの `time.process_time()`)の中央値は、50 万セルで `E` が 24.38 秒 → 8.72 秒、`X` が 37.58 秒 → 16.91 秒、10 万セルで `E` が 4.91 秒 → 1.86 秒、`X` が 7.95 秒 → 2.45 秒だった
- 修正後の 50 万セルの内訳(中央値に近い回)は、`E` がブック 2 つの読み込み 7.2 秒・射影 1.1〜1.3 秒、`X` がブック 2 つの読み込み 7.2〜10.0 秒・選択の照合 0.5〜0.6 秒・再構成と結果の検証 6.3〜7.4 秒だった
- 一時セッションのディスク使用量は、射影の写しを残すので 10 万セルで 4.4 MB → 7.3 MB、50 万セルで 23 MB → 38 MB に増えた
- 読み込みだけを別に測ると(50 万セルのブック 1 つ、gc は通常のまま)、修正前は 5.13 秒・5.04 秒(射影 3.62 秒・3.57 秒)、修正後は 5.54 秒・2.69 秒・2.52 秒(射影 0.45 秒・0.56 秒・0.28 秒)だった。修正後の 1 回目だけ遅かった

### 実 TUI での操作

- 修正後の 50 万セルのブックで、外側の lazygit で `E` を押してから選択画面に差分が出るまで 12.7 秒・12.3 秒・13.0 秒、`Space` は 0.69 秒、`X` を押してから完了のポップアップまで 12.9 秒・15.7 秒・18.1 秒だった(3 回。ほかのセッションの処理が同時に動いていた)

### 見つかった問題と対応

- 1 回目の実 TUI(50 万セル)で、`X` の後すぐに `q` で閉じると、「Excel の部分ステージを反映しました。」の後に「Excel の部分ステージに失敗しました: [WinError 32] プロセスはファイルにアクセスできません。別のプロセスが使用中です。: '…\lazygit-excel-stage-…\picker'」と出て、「Enterキーを押してlazygitに戻る」で止まった。index は正しく更新されていた。`%TEMP%` に `picker`・`base.xlsx`・`work.xlsx`・`session.json`・`config.json` が残り、数秒後には手で消せた
- lazygit 0.66.0 の Windows 版は、終了しても実行中の差分のコマンドを止めなかった(2026-10-08 の Windows の検証で見つけた性質と同じ)。`X` の後に lazygit が大きい差分を作り直している途中で終了すると、そのコマンドが選択画面のリポジトリを使ったまま残り、一時フォルダーの後片付けが失敗して、成功した後に失敗と表示していた
- 修正前の版も同じ後片付けの処理だった。今回の変更で、一時セッションのフォルダーを消せないときは 0.5 秒ごとに最大 20 回やり直し、それでも消せなければ警告だけを出すようにした
- 対応後の 2 回(同じ 50 万セルの操作で、`X` の後すぐに `q`)は、0.66 秒・0.87 秒で外側に戻り、端末には「反映しました」だけが出て、一時フォルダーは残らなかった。この 2 回で使用中の競合が実際に起きたかは、画面からは分からなかった。やり直しと警告の動きは単体テストで確かめた

## Windows 11 での Excel の部分ステージの検証（2026-10-09）

[Excel の部分ステージ](#excel-の部分ステージ2026-10-08)を Windows 11 の実機で確かめ、見つかった問題に対応した。

- 環境: Windows 11 Pro(ビルド 26300)、AMD Ryzen AI MAX+ 395(32 スレッド)、Git 2.55.0.windows.5、Python 3.14.8(scoop)、openpyxl 3.1.5、xlrd 2.0.2、lxml 6.1.3、lazygit 0.66.0・delta 0.20.1(scoop)、WezTerm 20260905-153129-092dcf70。Linux 側の確認には同じ PC の WSL の AlmaLinux 10(Python 3.12.13、Git 2.52.0)を使った
- 方法: `GIT_CONFIG_GLOBAL`・`XDG_CONFIG_HOME`・`XDG_DATA_HOME` と `--install-dir` を一時フォルダーに向けて導入し、実際のグローバル Git 設定、`%LOCALAPPDATA%` の導入先、lazygit の設定は変更していない(検証の前後でハッシュが一致)。lazygit は同梱 `config.yml` を `--use-config-file` で読み込み、利用者の WezTerm 設定のまま 160 列×45 行の窓で起動した。キーは `wezterm cli send-text` で送り、画面は `wezterm cli get-text` で読み取った。`NO_COLOR` は外した

### 導入と自動テスト

- `python scripts/setup-excel-diff.py --install-dir <一時フォルダー>` で、lxml を含む依存関係、変換と部分ステージのスクリプト、`alias.excel-stage` がそろった(pip のダウンロードを含めて 12.6 秒)。`--check` は設定を変えずに成功した
- PR の版では、Windows で 56 テストのうち 2 件が失敗した(別の 1 件は Windows では skip)。どちらもテスト側の問題で、Windows のファイル名に使えない `*` `?` `:` を含む名前を作ろうとしたことと、`write_text` で書いた比較用のファイルが CRLF になったことが原因。Windows では角かっこを含む名前で pathspec を確かめ、比較用のファイルは LF のバイト列で書くようにした
- 下記の修正後、Windows で 59 テストが成功し(POSIX の実行ファイルを使う alias のテスト 1 件は skip)、WSL の AlmaLinux 10 では 59 テストすべてが成功した

### 実 TUI での操作

- 日本語名のブック `売上表.xlsx`(シート `売上 表` と `備考`)の A2・A30・備考の B4 を変更し、別ファイル `notes.txt` をステージした状態で、`E` → `Enter` → `Space` → `X` → `q` を操作した。A2 だけがステージされ、A30・B4、作業ファイルの全バイト、`notes.txt` のステージは元のままだった。続けて A30 を同じ操作で選ぶと、A2 を残したまま追加された
- `Space` で選んでから `X` を押さずに `q` で戻ると、index ファイルのハッシュは変わらなかった。`X` を 2 回押すと 2 回目は「この選択は反映済みです」と表示され、index は変わらなかった
- サブフォルダーから `git excel-stage -- 売上表.xlsx` を実行すると `資料/売上表.xlsx` の選択画面が開き、キャンセルできた(Windows では skip される alias のテストの代わり)
- 空白を含む導入先でも `X` が動いた。lazygit 0.66.0 の Windows 版はカスタムコマンドを `cmd /s /c "…"` で実行するため、引用符で囲んだパスがそのまま渡る
- 新規ファイルや `.txt` で `E` を押すと、端末にエラーが出て「Enterキーを押してlazygitに戻る」で止まり、戻ると lazygit が「exit status 1」を表示した。成功とキャンセルの端末への表示は、同梱設定の `promptToReturnFromSubprocess: false` によりすぐ lazygit に戻るため読めないが、結果は専用画面のポップアップで確認できる
- 100 列×30 行でも表示は崩れず、長い行は delta が折り返した。改行・タブを含むセルは `\n`・`\t` と表示される(閲覧用の textconv と同じ)
- `%TEMP%` の `lazygit-excel-stage-*` は、どの操作の後も残らなかった

### 見つかった問題と対応

- 日本語版 Excel が文字列に付けるふりがな(`rPh`・`phoneticPr`)をリッチテキストとみなしていたため、ふりがな付きのセルを変更すると部分ステージが拒否された(日本語版 Excel と同じ形の sharedStrings を持つブックで再現)。ふりがなは比較の対象外のまま、文字ごとの書式だけを拒否するようにした。選んだセルにはふりがなを引き継がない
- 部分ステージのたびに `calcPr` に `forceFullCalc="1"` を書いていた。Excel の「常に完全再計算」の設定としてブックに残るため、読み込み時に一度だけ再計算する `fullCalcOnLoad` だけにした
- 選んだセルごとに sheetData の全行を並べ直して探していたため、10 万セルのブックで 1,000 セルを選ぶと `X` に 26.5 秒かかった。行を一度だけ索引にし、要素ごとの QName の生成もやめて 4.6 秒になった
- 50 万セルのブックでは、`E` を押してから約 20 秒、端末に lazygit のコマンド行しか出ず、止まったように見えた。ブックを読み込む直前に「Excel を読み込んでいます」と表示するようにした
- 対象外の拡張子への案内が「旧形式は全体をステージ」だけで、`.txt` などに合わなかったため、「それ以外のファイルは全体をステージ」に改めた

### 速さとメモリ

## Windows 11 での Excel 差分の検証と大きいブックへの対応（2026-10-08）

[Excel の textconv 差分表示](#excel-の-textconv-差分表示2026-10-08)を Windows 11 の実機で確かめ、見つかった待ち時間の問題に対応した([大きいブックの表示](https://github.com/ryo-aoki-pc/lazygit/blob/1ff98e242cd03a363200d9749b95ebbb52b1503d/docs/excel-diff.md#大きいブックの表示))。

- 環境: Windows 11 Pro(ビルド 26300)、AMD Ryzen AI MAX+ 395(32 スレッド)、Git 2.55.0.windows.5、Python 3.14.8(scoop)、openpyxl 3.1.5、xlrd 2.0.2、lazygit 0.66.0・delta 0.20.1(scoop)。Linux 側の確認には同じ PC の WSL の AlmaLinux 10(Python 3.12.13、Git 2.52.0)を使った
- 方法: `HOME`・`USERPROFILE`・`LOCALAPPDATA` を一時フォルダーに向けて導入し、実際のグローバル Git 設定は変更していない。lazygit は ConPTY の 140列×40行で起動して pyte で画面を読み取り、`CONFIG_DIR` に同梱 `config.yml` の写しを置いた。`NO_COLOR` は外した

### 導入と自動テスト

- PowerShell の `python scripts/setup-excel-diff.py` で仮想環境・依存関係・Git 設定がそろった(初回は pip のダウンロードを含めて 42 秒)。再実行と `--check` の前後で設定が変わらず、`XDG_CONFIG_HOME` / `XDG_DATA_HOME` を変えても `--check` が成功した
- 既存の `core.attributesFile = ~/.gitattributes`(CRLF・末尾の改行なし)はそのまま残り、Excel の行だけが追記された。6 形式の大小文字混在の拡張子が `diff=excel` になり、`.xlsb` / `.csv` は対象外だった
- 日本語・空白・単一引用符を含む `--install-dir` でも、Git for Windows の sh から変換が動いた
- [`tests/test_excel_textconv.py`](../../tests/test_excel_textconv.py) の 16 テストが、Windows(仮想環境の Python 3.14.8)と WSL の AlmaLinux 10 の両方で成功した。変更前の 10 テストも Windows で成功していた

### lazygit での表示

- 変更・ステージ済み・追加・削除・未追跡・コミットの `.xlsx` / `.XLSX` と、ステージ済みの `.xls` の差分が delta の左右比較で表示された。`|` で切り替えた内蔵表示も同じ内容だった
- ファイル一覧の `Space` でステージした `.xlsx`・`.XLSX`・`.xls` は、インデックスの内容が元のファイルとバイト単位で一致した
- ファイル名に日本語を含むと、delta の見出しは `\345\243\262…` のような 8 進数の表記になる(Git の `core.quotePath` の既定値による。Excel 以外のファイルも同じ)。ファイル一覧の名前は正しく表示される
- `binary=true` のため、ファイル一覧の変更行数とコミットの `--stat` には Excel の行数が出ず、`Bin` と表示される
- 値だけが変わった行は、delta が変更前後を同じ段に並べないことがある(例: `B2 1000` → `B2 1200` は 1 段ずれ、`B2 300` → `B2 350` は同じ段に並んだ)。どちらも左右の同じ行番号の近くに表示される

### 大きいブックで見つけた問題と対応

- 50 万セル(1.9 MB)の `.xlsx` は、1 回の変換に 6.1 秒、キャッシュなしの `git diff` に 14.4 秒かかった。この間も lazygit のキー操作(カーソル移動・`Enter`・`Esc`・`Space`)は 20〜70 ms で反応したが、差分の欄は `loading...` のままだった
- lazygit 0.66.0 の Windows 版は、別のファイルを選んでも実行中の差分コマンドを止めない(ソースの `Terminate` が Windows では何もしない)。重いブック 2 つを順に選んでから小さいファイルへ移ると、変換が最大 4 本同時に走り、移動した後も約 27 秒間 CPU を使い続けた
- 起動直後の lazygit はルート(`/`)を選び、全ファイルの差分を作る。このブックを 2 つ変更したリポジトリでは、60 秒待っても差分の欄が表示されなかった
- 対応として、変換が 2 秒で終わらなければ「変換中」の内容を返し、残りを優先度の低い裏の処理 1 本で順に変換して、結果を内容のハッシュごとにキャッシュするようにした。シートの展開後の大きさから 2 秒で終わらないと分かるブック(展開後 16 MB 超)は待たずに返す。Git の変換キャッシュは仮の内容を保存してしまうため使わない
- 同じ操作で、ルートの差分は 2.9〜4.3 秒で表示され、重いブックを選ぶと 0.01 秒以内に「変換中」が表示された。変換は最大 2 本(表示中の 1 本と裏の 1 本)で、裏の変換が終わると lazygit の 10 秒ごとの更新で、選んだままの差分も完全な内容に切り替わった
- 片方の版だけが変換済みの場合は、その版のセルが全部消えたように表示されるが、「変換中」の行がシート名の行より前に来るため、差分の先頭に出た(lazygit とテストで確認)
- `.xls` の変換は、列名の計算のためだけに openpyxl を読み込んでいた(1 回あたり約 0.24 秒)。自前の計算に替え、1 万セルの `.xls` の変換が 0.31 秒から 0.19 秒になった。キャッシュから返すときは 0.13 秒(小さいブック)〜0.21 秒(10 万セル)だった

### 表示の速さ(変更前後)

lazygit でファイルを選んでから、差分の欄に変更したセルが出るまでの秒数(中央値)。測定中は別のアプリが CPU を 40〜90% 使っていたため、変更前と変更後の版を同じリポジトリで交互に 3 回ずつ測った。「初回」は変換結果のキャッシュを消してから選んだ時間(3 回)、「2 回目以降」はキャッシュがある状態で選び直した時間(12 回。`.xls` は 6 回)。変更前の 2 回目以降は、変更前の版(Git のキャッシュ)を使い、作業中の版だけを変換している。

| 選んだファイル | 変更前 初回 | 変更前 2 回目以降 | 変更後 初回 | 変更後 2 回目以降 |
| --- | ---: | ---: | ---: | ---: |
| テキスト(基準。40 行の 1 行変更) | — | 0.21 | — | 0.18 |
| `.xlsx` 100 セル | 0.99 | 0.50 | 0.92 | 0.48 |
| `.xlsx` 1 万セル | 1.11 | 0.57 | 0.97 | 0.49 |
| `.xlsx` 10 万セル | 2.61 | 1.43 | 2.77 | 0.52 |
| `.xls` 1 万セル | 0.97 | 0.71 | 0.67 | 0.54 |

- Excel の差分を設定しない場合(バイナリ表示)、同じ `.xlsx` を `git diff | delta` で表示するまでは 0.15〜0.23 秒だった
- 起動からルートの差分が出るまでは、変更前 2.03 秒・変更後 1.76 秒だった(キャッシュがある状態、各 3 回の中央値)。Excel の差分を設定しない場合は 1.2〜1.6 秒だった
